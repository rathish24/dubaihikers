# Database Design

Supabase PostgreSQL is the application database for the event catalogue and event registrations. Persistence is isolated from the web UI through the standalone `@dubaihikers/events` and `@dubaihikers/registrations` packages.

## Ownership

- `packages/events/src/types.ts` owns the persisted event domain.
- `packages/events/src/repository.ts` defines the replaceable data-source contract.
- `packages/events/src/supabase.ts` maps Supabase rows into domain events.
- `packages/registrations` owns registration validation, repository contracts, and Supabase mapping.
- `apps/web/data/events.ts` formats domain events for the existing UI.
- `supabase/migrations` owns database structure and access policies.
- `supabase/seed` owns the versioned sample catalogue.

The component and feature layers do not import Supabase code, keys, table names, or snake-case database fields.

## Event access

The public website reads only rows whose status is `published`. Row-level security prevents anonymous clients from writing events. Administrative writes use protected server or local tooling with a Supabase secret key.

The web query:

- filters to published events;
- excludes past events by default;
- sorts by `starts_at`;
- disables framework caching so catalogue changes are visible on the next request.

## Capacity

`capacity` is the maximum group size. Confirming or cancelling a registration updates `available_slots` in the same transaction while locking the event row. Events with no remaining capacity are shown as fully booked.

## Event registrations

`event_registrations` stores one booking for one event. It contains an optional authenticated `user_id` for future account retrieval while continuing to support guest checkout. Contact details and `customer_notes` are snapshots of what the customer supplied for that booking.

The registration stores `number_of_hikers`, the event price and currency at booking time, and a generated total. Booking status and payment status are separate. The current no-payment flow creates confirmed registrations with `payment_status = 'not_required'`. Waitlisting is not exposed in the current customer flow.

The `create_event_registration` database function locks and rechecks the event, copies trusted pricing from `events`, and inserts the registration atomically. Its idempotency key makes retrying the same browser request safe.

### Registration model

| Field | PostgreSQL type | Required | Description |
|---|---|---:|---|
| `id` | `uuid` | Yes | Internal primary key generated by PostgreSQL. |
| `reference_number` | `text` | Yes | Unique customer-facing reference such as `DH-2F3B54E823`. |
| `event_id` | `uuid` | Yes | Foreign key to `events.id`. The event cannot be deleted while registrations reference it. |
| `user_id` | `uuid` | No | Optional foreign key to `auth.users.id`. It is null for guest bookings. |
| `contact_name` | `text` | Yes | Name of the main booking contact, limited to 2-120 characters. |
| `contact_email` | `text` | No | Optional normalized contact email, limited to 254 characters. |
| `contact_phone` | `text` | Yes | WhatsApp or mobile number in international E.164 format. |
| `number_of_hikers` | `smallint` | Yes | Number of event places requested, limited to 1-20. |
| `customer_notes` | `text` | No | Optional message supplied by the customer, limited to 1,000 characters. |
| `unit_price` | `numeric(10,2)` | Yes | Trusted event price per hiker copied when the registration is created. |
| `total_amount` | `numeric(10,2)` | Yes | Generated value calculated as `unit_price * number_of_hikers`. |
| `currency` | `char(3)` | Yes | ISO-style uppercase currency code, normally `AED`. |
| `status` | `registration_status` | Yes | Registration lifecycle state. Defaults to `pending`. |
| `payment_status` | `registration_payment_status` | Yes | Payment lifecycle tracked separately from registration status. |
| `payment_provider` | `text` | No | Future payment provider name. |
| `payment_reference` | `text` | No | Future provider transaction reference, unique within a provider. |
| `idempotency_key` | `uuid` | Yes | Unique request identifier that prevents duplicate registrations on retry. |
| `waiver_accepted_at` | `timestamptz` | Yes | Time at which the customer accepted the participation waiver. |
| `confirmed_at` | `timestamptz` | No | Time at which places were confirmed and reserved. |
| `cancelled_at` | `timestamptz` | No | Time at which a cancelled or refunded registration ended. |
| `created_at` | `timestamptz` | Yes | Registration creation time. |
| `updated_at` | `timestamptz` | Yes | Most recent registration update time. |

### Registration statuses

| Value | Capacity effect | Meaning |
|---|---:|---|
| `pending` | None | Registration is being processed or awaits a future action. |
| `confirmed` | Reserves places | Registration is confirmed. |
| `waitlisted` | None | Reserved for possible future use; not exposed by the current UI. |
| `cancelled` | Releases places | Registration was cancelled. |
| `refunded` | Releases places | A future paid registration was refunded. |

### Payment statuses

| Value | Meaning |
|---|---|
| `not_required` | Current registration flow requires no online payment. |
| `pending` | Payment has not completed. |
| `paid` | Payment completed successfully. |
| `failed` | Payment attempt failed. |
| `refunded` | Payment was returned to the customer. |

### Integrity rules

- A registration belongs to exactly one event.
- A registration may optionally belong to one authenticated user.
- Only confirmed registrations reduce `events.available_slots`.
- Confirming, changing the hiker count, cancelling, refunding, or deleting a confirmed registration updates capacity transactionally.
- A registration cannot be moved to another event.
- Confirmed registrations require `confirmed_at`.
- Cancelled and refunded registrations require `cancelled_at`.
- Browser clients cannot provide authoritative price, total, currency, status, or payment values.
- `reference_number`, `idempotency_key`, and provider payment references are protected against duplicates.

## Registration email deliveries

`registration_email_deliveries` records each booking-reference notification independently from the registration. One `booking_reference` delivery is allowed per registration.

| Field | PostgreSQL type | Description |
|---|---|---|
| `id` | `uuid` | Delivery primary key. |
| `registration_id` | `uuid` | Parent registration. Deleting the registration deletes its delivery history. |
| `message_type` | `text` | Stable template identifier, currently `booking_reference`. |
| `recipient` | `text` | Address used for this delivery attempt. |
| `provider` | `text` | Delivery provider, currently `resend`. |
| `provider_message_id` | `text` | Unique identifier returned by the provider. |
| `status` | `email_delivery_status` | Final one-time result: `delivered` or `undelivered`. |
| `last_error` | `text` | Safe delivery error for an undelivered email, limited to 500 characters. |
| `delivered_at` | `timestamptz` | Successful provider handoff time. |
| `created_at` | `timestamptz` | Row creation time. |
| `updated_at` | `timestamptz` | Most recent status update. |

Delivery records are private and writable only through the server-side service role. Failed emails are recorded as `undelivered` and are not retried automatically.

## Seed data

`supabase/seed/events.json` contains ten events across Beginner, Moderate, Advanced, and Expert levels. `pnpm db:seed:events` upserts these rows using the unique event slug.

## Security

- RLS is enabled on `public.events`.
- Anonymous and authenticated visitors may select published events.
- No public insert, update, or delete policy exists.
- Registration writes are available only to the server-side service role.
- Authenticated customers may read only registrations linked to their own user ID.
- The Supabase secret key is never exposed to the browser.
- Public meeting-point labels do not contain sensitive final instructions.
